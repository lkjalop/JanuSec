Category: Unauthorised access - illicit OAuth consent · DREAD: 8.0 · Attack complexity: low

Timeline: 2026-04-13T13:37:42+00:00 → 2026-04-28T20:42:43+00:00 (15 days); assessed 2026-07-07T00:00:00+00:00

Affected: martin.chen · 4 host(s) · Active Directory, Data / Network, Endpoint / Windows, SaaS / M365 · · blast radius: multi-host campaign

Root cause: Initial access via a malicious OAuth consent grant succeeded because control A.5.15 (Access control) was not effective. The intrusion then progressed: a malicious OAuth consent grant -> Kerberoasting of AD service accounts -> WMI lateral movement -> sustained data exfiltration.

Response actions:

  • [P1/24h] Revoke the malicious OAuth consent grant and audit app registrations for excessive scopes. (Identity)
  • [P1/24h] Reset the targeted service-account password and rotate krbtgt; enforce AES + long SPN passwords. (Identity)
  • [P1/24h] Isolate the source and destination hosts; audit WMI/DCOM remote-exec permissions. (SOC)
  • [P1/24h] Block egress to the destination; quantify data exposure; trigger breach-notification assessment. (SOC/DLP)

Lessons learned:

  • Quarterly app-registration and consent-grant review
  • gMSA migration; quarterly service-account audit
  • Just-in-time admin access
  • Data classification; egress-anomaly monitoring
  • Disable end-user OAuth consent; require admin-consent workflow for high-risk scopes
  • Enforce AES-only Kerberos; 25+ char gMSA passwords; remove SPNs from user accounts; Tier-0/1/2 admin model
  • East-west microsegmentation; restrict WMI/DCOM to admin jump hosts; host firewall deny-by-default
  • Egress filtering with allow-listed destinations; DNS security; data-egress baselining

Breach notification required — NDB Scheme / GDPR Art.33 (72h)
