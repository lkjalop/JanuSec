⬆ Three Upload Paths — Where to Click What

Path A — Manual XLSX (the main demo)

  1. Open the LIVE Console
    Navigate to http://localhost:8080/. You'll see the dashboard with Recent Decisions feed.
  2. Click "Upload Logs" in the sidebar or the drop-zone
    Drag in Cyberstash_csv2.xlsx from C:\AI\janusec\. The drop-zone accepts .xlsx, .csv, .json, .evtx, .pcap.
  3. Watch the pipeline run
    Decisions populate in real-time. The status bar updates: Critical: 2 → 8, High: 5. This is the detection engine. You can also run the full pipeline directly: python scripts/run_cyberstash_full_pipeline.py --server http://localhost:8080
  4. Click "Export Investigation Report"
    In the right rail. Opens the full HTML report with all 5 persona tabs. Alternatively: /api/v1/report/ingestion?format=html&include_model=true&include_scenarios=true
  5. Switch persona tabs
    Click [Executive] → [Compliance] → [Threat Hunter]. Show GDPR clock, blind spots, MITRE coverage. Each tab is a different audience.
  6. Click "Create Incident"
    Fires POST /api/v1/incidents. Shows confirmation toast. In production this writes to your SIEM/ticketing system.
Path B — AWS CloudTrail
1. Open: http://localhost:8080/static/integrations.html 2. Under "AWS" section → click "Paste CloudTrail JSON" or use API: curl -X POST http://localhost:8080/api/v1/connectors/aws/ingest \ -H "x-api-key: devkey123" \ -H "content-type: application/json" \ -d @artifacts/reports/executive_review/aws/sample_cloudtrail.json 3. Result: executive HTML report auto-generated GET http://localhost:8080/api/v1/report/ingestion?format=html&persona=executive
Path C — Azure Entra ID Sign-ins
1. Same flow, different endpoint: curl -X POST http://localhost:8080/api/v1/connectors/azure/ingest \ -H "x-api-key: devkey123" \ -H "content-type: application/json" \ -d @artifacts/reports/executive_review/azure/sample_signinlogs.json 2. Pre-built artifacts available in: artifacts/reports/executive_review/aws/ (9 HTML+PDF pairs) artifacts/reports/executive_review/azure/ (9 HTML+PDF pairs)

🎛 Report Gating — 12 Toggles (for live demo tuning)

Pass report_options in the API payload to turn sections on/off without modifying code. All ON by default — only set false to suppress.

include_mitre_table
true ← MITRE ATT&CK coverage grid
include_raw_data
true ← raw events appendix (SOC/Forensics)
include_pasta_register
true ← PASTA risk register table
include_hunt_queries
true ← KQL/SPL hunt queries (Threat Hunter)
include_sigma_rules
false ← SIGMA output (off by default)
include_dread_breakdown
true ← DREAD score breakdown table
include_beacon_analysis
true ← C2 beacon interval analysis
include_blind_spots
true ← coverage gap listing (Threat Hunter)
include_process_tree
true ← process ancestry table (Forensics)
include_full_escalation
true ← all CRITICAL events (no cap)
include_framework_citations
true ← ISO/NIST citations (Compliance)
compact_mode
false ← compact layout for printing

Example: executive-only compact report

POST /api/v1/report/generate_pdf
{
  "persona": "executive",
  "report_options": {
    "include_raw_data": false,
    "include_hunt_queries": false,
    "include_sigma_rules": false,
    "compact_mode": true
  }
}

❓ CEO Q&A Preparation

"How accurate is it?"

On the Cyberstash_csv2 dataset: 8/15 events confirmed malicious, confidence 0.91. DREAD scores: 8.6/10 average for CRITICAL tier. The system uses corroborating evidence from multiple sheets — a single suspicious event doesn't trigger CRITICAL; it requires matching factors across Network + EDR + C2 channels.

"What happens when it's wrong?"

False positives are tracked via /api/v1/admin/factors/telemetry. Operators can adjust factor weights via the scoring sliders without code changes. The Blind Spots section in Threat Hunter reports explicitly flags where coverage is missing — we don't pretend coverage we don't have.

"Is this GDPR-compliant itself?"

The platform detects GDPR breach obligations; it does not itself process PII beyond what's in the uploaded logs. On-premise deployment means no data leaves the customer environment. The 72h clock starts at report generation time (discovery moment), not the historical incident timestamp.

"How does it scale?"

The API layer is FastAPI (async), stateless, horizontally scalable behind a load balancer. HopGraph correlation and Redis are optional — the core works without them for demo/PoC. Session persistence uses flat JSON files; swap to PostgreSQL or S3 for production.

"What's the deployment story?"

Windows: double-click start_server.bat. Linux/Docker: single container (included Dockerfile). Azure: Terraform deployment scripts in azure/ — see AZURE_TERRAFORM_DEPLOYMENT_SUMMARY.md.

"When is it production ready?"

The detection engine, API, PDF/HTML reports, and GDPR compliance module are production-ready today. The roadmap items are: HopGraph Redis with persistent storage, email DKIM verification (install dkimpy), and the multi-tenant auth layer. None of these are blockers for a pilot deployment with a single tenant.
